## MISSION
A **local, fully-offline** system on an **Apple M1, 8GB** Mac that (a) answers questions over 15+ long documents containing numeric tables, and (b) verifies factual claims against those documents. Graders reward **honesty, rigor, and trustworthiness** over demo polish. Every design choice must be defensible in a 2-page memo.

## HARD CONSTRAINTS (never violate)
1. **Offline at runtime** — works with the network unplugged. One local open-weight model, **7–8B class, quantized to INT4**. **No cloud LLM APIs anywhere** (QA, data-gen, verifying, judging). Pre-downloading weights/data is fine.
2. **Numbers are NEVER generated by the model.** Every numeric answer is **computed in Python/pandas**. The LLM only selects the relevant table + cells + operation; a code function does the arithmetic and returns the value.
3. **Every answer carries a citation** — page for prose, `{doc, page, table_id, cell}` for numbers.
4. **Tables survive ingestion as structured data** (SQLite/DataFrame), never flattened into prose.
5. **Report failures honestly.** Log each miss with its mechanism. Hiding weaknesses fails the gate.
6. Maintain **`AI_LOG.md`** continuously: what you (the assistant) did each phase, and anything you got wrong that I corrected. Feeds the required AI-disclosure in the memo.

## MODEL — Qwen2.5-7B-Instruct (LOCKED, do not substitute)
Use **`mlx-community/Qwen2.5-7B-Instruct-4bit`** (pre-quantized) as the working model, converted further as needed for the Phase 5 ladder. Chosen over Llama-3.1-8B-Instruct for two reasons: (1) **Apache 2.0, ungated** on Hugging Face — no license-acceptance wait; (2) benchmarks stronger on **numeric/tabular reasoning**, which is the core of this task. Do not swap models mid-build without flagging it to me first.

## HARDWARE PLAN — Apple M1, 8GB, INT4 only (LOCKED)
This is a **base M1 (7–8 core GPU), 8GB unified memory** — capable but modest and memory-tight. macOS uses ~3–4GB → only ~4–5GB usable. Model-weight footprints for a 7B model: **INT4 ≈ 4GB (fits), INT8 ≈ 7GB (OOM/swap), FP16 ≈ 14GB (infeasible).**
- Run **everything on the INT4 model.** Keep context small; cap KV-cache with `--max-kv-size`; batch size 1; close other apps during runs.
- Expect **modest tokens/sec on M1** — that's fine. The eval says absolute speed doesn't matter; methodology and honest per-type analysis do.
- **Do NOT use speculative decoding** here — a draft model costs extra memory we don't have on 8GB.
- Quantization ladder (Phase 5) still needs 3 rungs: **full real INT4 results**; **attempt INT8** and record the real OOM/swap behaviour; **FP16 = infeasible** with memory arithmetic shown. Never fabricate FP16/INT8 numbers — the honest wall is a valid finding, arguably the most valuable one in the whole deliverable.

## STACK (MLX-native — do NOT use HuggingFace `transformers` for the LLM, CUDA, bitsandbytes, or nvidia-smi; none apply on Mac)
- **LLM inference:** `pip install mlx-lm`. `from mlx_lm import load, generate`, using `mlx-community/Qwen2.5-7B-Instruct-4bit`.
- **Quantization ladder (Phase 5):** `from mlx_lm import convert`, one base model → three artifacts:
  - `convert(hf_repo, mlx_path="m-fp16", dtype="float16")`  *(kept for arithmetic; won't run on 8GB)*
  - `convert(hf_repo, mlx_path="m-int8", quantize=True, q_bits=8)`
  - `convert(hf_repo, mlx_path="m-int4", quantize=True, q_bits=4)`  ← the working model
  Keep `q_group_size` equal across rungs so it is the *same model* at three precisions.
- **Embeddings (local):** `sentence-transformers` with a small model (`bge-small-en` ~130MB or `all-MiniLM-L6-v2`). NOTE: despite the name, this is **not** the heavy HF `transformers` LLM path — it's a tiny embedding model running on PyTorch's **MPS** backend, and is fine alongside INT4 on 8GB.
- **Vector store:** FAISS-cpu (or Chroma).
- **PDF / tables (Mac-native, pure Python):** **`pdfplumber`** — use `page.extract_tables()` to keep tables as rows/columns WITH page numbers. **Do NOT use PyPDF2/pypdf for tables** — those only pull flat text and destroy table structure, which breaks constraint #4. For prose/page text specifically, `PyMuPDF` (fitz) is fine and fast alongside pdfplumber for tables.
  - **Fallback for stubborn tables: `camelot`.** Flag before installing — camelot requires **Ghostscript as a system dependency**, which is an extra `brew install ghostscript` step outside pip. Only reach for it if pdfplumber genuinely fails on a specific document; don't default to it.
  - **If any corpus doc is scanned/image-only** (text won't select), add OCR via `pytesseract` + `pdf2image`. Prefer text-based PDFs to avoid this entirely — check before adding to corpus.
- **Measurement (Mac-correct):**
  - **Memory:** `import mlx.core as mx; mx.reset_peak_memory(); <run>; peak = mx.get_peak_memory()`. **Document the caveat:** on Metal this can under-report (~2x). Cross-check with Activity Monitor "Real Memory" or `footprint <pid>`; report **both** numbers. Also watch "Swap Used" — on 8GB M1, note if runs push swap.
  - **Latency:** wrap generation in `time.perf_counter`; log per-query wall time; compute **P50 and P95** across the 20 gold-set runs; record time-to-first-token if easy.

## PHASE 1 — Ingestion: tables as structured data (foundation for 1A)
1. `download_corpus.py` fetches **15+ long public docs with numeric tables** (annual reports / agency / technical publications) into `corpus/`. Don't commit the PDFs — the script re-fetches (see .gitignore).
2. Ingestion: **PyMuPDF** for prose chunks **with page numbers preserved**; **pdfplumber** for tables into SQLite with schema `tables(doc_id, page, table_id, row, col, value, unit, header)`. Preserve units explicitly — several planted errors later hinge on units living separately from values.
3. Build + persist the embedding index over prose chunks; keep the table store separate.
4. **Validation:** dump 5–10 sample tables to `results/ingestion_check.md`; eyeball that numbers/units survived; **log every table that broke and why** (this honesty is graded).
5. Commit + push. **Status note.**

## PHASE 2 — QA with code-computed numerics + citations → **1A**
1. **Router:** classify each question `prose` / `numeric` / `multi-doc` (rules + LLM fallback; mark `# DECISION:`).
2. **Prose path:** retrieve top-k chunks → LLM answers **strictly from retrieved text** → return answer + `{doc, page}`.
3. **Numeric path (critical):**
   - LLM outputs a *structured plan only*: `table_id`, cell(s), operation (`sum`/`diff`/`ratio`/`pct_change`/`lookup`).
   - A **Python function executes** the operation over the SQLite cells and returns the number.
   - Return: computed value + `{doc, page, table_id, cell(s)}` + operation. **The model never emits the final number.**
4. **Multi-doc path:** retrieve/compute across ≥2 docs; cite each source.
5. One interface `answer(q) -> {answer, citations, path_taken, confidence}` + CLI (`python -m src.qa.ask "..."`).
6. Run against the **INT4 model** — this is the working baseline for the whole build.
7. Commit + push. **Status note** with 2–3 example Q→A→citation transcripts.

## PHASE 3 — Gold set + planted-error summary → **1B**
1. `gold_set.json`: **20 pairs = 8 prose + 8 numeric + 4 multi-doc**, each `{question, expected_answer, expected_citation, type}`.
2. `summary.md`: **1 page, exactly 15 claims**, of which **6 are planted errors — one of each type**: wrong number · right-number-wrong-period · misattribution · unsupported inference · unit error · cross-document contradiction. Other 9 true & supportable.
3. **Hidden key:** `answer_key.json` (per claim: verdict + error-type + source) → **encrypt to `answer_key.enc`** (Fernet/`cryptography`); keep plaintext out of git. Reveal only at the walkthrough.
4. You draft; **I review every question and every planted error** before we proceed — flag for my review, don't assume approval.
5. Commit + push (`answer_key.enc` only, never plaintext). **Status note.**

## PHASE 4 — Verification layer → **1C**
1. Per claim (15): retrieve evidence (and **recompute in code** for numeric claims) → **verdict ∈ {supported, contradicted, unverifiable}** (all three reachable) + **evidence citation** + **confidence**.
   - `contradicted` = evidence found and disagrees; `unverifiable` = no supporting evidence located. Make this explicit in code — don't let these two conflate.
2. **Scoring:** decrypt key at eval time; **precision & recall** (positive class = "planted error → should be contradicted") + **3-way confusion matrix**.
3. **Surface ≥1 genuine miss** with its **mechanism** (e.g. "unit error slipped through because the unit lived in the header, not the cell, so recompute compared raw magnitudes"). Don't paper over it.
4. Output `results/verification_report.md` (numbers + miss write-up).
5. Commit + push. **Status note.**

## PHASE 5 — Quantization ladder → **1D** (INT4 real; INT8/FP16 honest)
1. Build the three artifacts with `mlx_lm.convert`.
2. **INT4 (full):** run 20 gold questions → **accuracy per question type** (prose/numeric/multi-doc), **P50/P95 latency**, **peak memory** (MLX API + Activity Monitor, both reported).
3. **INT8:** attempt to load/run on 8GB; **record actual behaviour** (loads-but-swaps / OOM at step X) with timestamps + swap observations.
4. **FP16:** mark **infeasible**; show `7B × 2 bytes ≈ 14GB > ~4-5GB usable` + macOS overhead reasoning.
5. `results/quant_table.md`: tradeoff table (rows FP16/INT8/INT4; cols per-type accuracy, P50, P95, peak mem) + **deployment recommendation** ("ship INT4 on edge Macs because …"). Predict + check where damage concentrates (numeric usually degrades first — cell-lookup precision is unforgiving to rounding) and why.
6. Commit + push. **Status note.**
